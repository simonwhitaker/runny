## 1. Wire format (verified, from [SPEC] unless noted)

### Framing

- `OSC` is `ESC ]` (0x1B 0x5D). `ST` is **either** `ESC \` (0x1B 0x5C) **or** `BEL` (0x07), so both terminators are allowed. [SPEC §Conventions]
- Grammar [SPEC §Syntax]:
  ```
  OSC 7501 ; pairs ST        report
  OSC 7501 ; ? ST            feature detection

  pairs    := pair (":" pair)*
  pair     := key "=" value
  key      := [a-z]+
  value    := [A-Za-z0-9_.,+/=-]*
  ```
- Pairs are separated by `:`. Values cannot contain `:` or `;`, so nothing needs escaping. Whitespace around keys and values is stripped.
- A malformed pair is skipped and the rest of the report is still used. Unknown keys MUST be ignored, which is how the protocol is extended. If a key repeats, the last value wins.
- The free-text values (`msg`, `title`) are **standard base64 of UTF-8**, and padding is optional. The decoded text MUST NOT contain control characters (U+0000–U+001F, U+007F, U+0080–U+009F), which rules out newline and tab. A report whose base64 fails to decode, or whose decoded text has a control character, is **discarded whole**.

### Keys [SPEC §Keys]

| Key | Values | Notes |
|---|---|---|
| `state` | `idle` \| `working` \| `done` \| `blocked` \| `error` \| `clear` | Required. A report with a missing or unknown state is ignored. |
| `id` | `segment ("/" segment)*`, where segment is `[A-Za-z0-9_.+-]{1,32}` | Absent means the root record. An invalid id causes the whole report to be ignored. It does not fall back to the root record. |
| `kind` | `permission` \| `question` \| `auth` | Only used with `blocked`. Unknown values are treated as absent. |
| `progress` | integer 0–100 | Only used with `working`/`blocked`. Absent means indeterminate (rev 0.3). |
| `app` | `[A-Za-z0-9_.+-]{1,32}` | Stable machine identifier (e.g. `cargo`), not a label. A record inherits it from its nearest ancestor. |
| `title` | base64 UTF-8 | A short label, for programs that report several records. |
| `msg` | base64 UTF-8 | One human-readable line. Terminals MAY shorten it and MUST NOT read meaning into it. |

### Limits [SPEC §Limits]

| Item | Limit |
|---|---|
| Whole sequence, OSC through ST | 4096 bytes |
| Key | 16 bytes |
| `msg` | 2732 bytes encoded, 2048 decoded |
| `title` | 256 bytes encoded, 192 decoded |
| `app` | 32 bytes |
| `id` | 128 bytes total, 32 per segment, 8 levels |
| Records per terminal | 256, with at least 64 required. Least-recently-updated records are evicted. |

A report that breaks any limit is discarded whole. Ghostty computes its body limit assuming the 2-byte `ESC \` terminator, so a BEL-terminated report gets one byte less than the spec allows. The spec permits this ("Terminals MAY choose lower limits"). [GH-PARSER `max_body_bytes`, L64]

### Records, replacement, clearing, nesting [SPEC §Records and ids, §States]

- The terminal keeps a **set of records keyed by id**. There is **no stack**. Each report **replaces its record completely**, so a key missing from a report is gone from the record afterwards. Repeat `app` in every report.
- `/` builds a parent/child tree (`build/test` is a child of `build`). The tree is used for clearing and `app` inheritance, and MAY be used for grouping. It means nothing else.
- `state=clear` removes the addressed record **and every record beneath it**. **With no id it removes every record on the terminal**, including records written by other programs.
- Records belong to the terminal, not to a screen, so switching to the alternate screen has no effect on them. RIS (full reset) removes all records. DECSTR (soft reset) does not.
- Lifetime: there is no heartbeat. When "the process attached to the terminal exits" or a new shell prompt begins (OSC 133 A), the terminal MUST drop `working`/`blocked` and MAY drop `idle`. `done`/`error` survive both events until the terminal decides to stop showing them.

### Example (from [SPEC §Examples])

```
OSC 7501 ; state=working:app=brew:msg=SW5zdGFsbGluZyB1cGRhdGVz ST   # Installing updates
OSC 7501 ; state=done:app=brew:msg=VXBncmFkZWQgMTIgcGFja2FnZXM= ST  # Upgraded 12 packages
```

Shell reference implementation from [SPEC §A shell function]:
```sh
printf '\e]7501;state=%s:msg=%s\e\\' "$1" "$(printf '%s' "$2" | base64 | tr -d '\n')"
```

## 2. Semantics (verified, [SPEC])

- The purpose is to let "a program tell the terminal what it is doing: idle, working, waiting on the user, finished, or failed, and why." The protocol "shares state and leaves presentation to the terminal". It deliberately avoids terms like notification, attention, or focus. [SPEC intro]
- State meanings [SPEC §States]: `idle` means at rest, waiting for the user's next instruction. `working` means running. `done` means the result is ready and the user has not seen it yet. `blocked` means the program can't continue without the user. `error` means it failed and stopped.
- When to set each state [SPEC §States]:
  - "When the user interrupts or cancels a program, report `idle`."
  - "A program that exits as soon as it finishes SHOULD report `done` or `error` right before exiting, so a record is left behind for the user to find."
- What terminals do with it is up to each terminal. Examples from implementers:
  - Rex shows session-picker indicators, spinners and blocked symbols on unfocused tab headers, and a Lua event `terminal.program_status_changed`. [SPEC §In Rex]
  - iTerm2 3.7.5: "The tab shows the most urgent status the program reported, along with its message and progress … each task that needs you can post its own notification." ([iTerm2 notes-3.7.5.txt @ 095beb4](https://github.com/gnachman/iTerm2/blob/095beb457dca2a5ed4a9f155dc2b4dc7d9ef34a2/docs/notes-3.7.5.txt))
  - kitty (unreleased 0.50.0): shown in the tab bar via a `tab.program_status` field for `tab_title_template`. ([kitty changelog @ 0e1b7f4](https://github.com/kovidgoyal/kitty/blob/0e1b7f4812bf297639999a362672c4271e42ed0c/docs/changelog.rst))
- Terminals SHOULD rate-limit side effects such as notifications and sounds. Ids, titles, and messages are never echoed back. [SPEC §Security]

## 3. Relationship to other sequences (verified, [SPEC §Relationship to other sequences])

- **OSC 9;4 (ConEmu progress):** It can say busy, a percentage, or error, but not "waiting on the user", and it carries no message or identity. It also collides with iTerm2's OSC 9 notification. "A program may send both." Terminals MAY map 9;4 to the root record but SHOULD stop mapping once they have received a 7501 report, because a mapped 9;4 would wipe out the 7501 record's `kind`/`msg`.
- **OSC 9 / 99 / 777 (notifications):** These are one-shot events with no current state. A terminal MAY generate a notification when a record changes.
- **OSC 133 (shell integration):** The shell emits it, not the program, so it only knows that a command is running or finished with an exit code. It interacts with 7501: **OSC 133 A drops `working`/`blocked` records.**
- **OSC 0/2 (titles):** These are unstructured. Programs overload them with spinners. The root record's label "is normally the window title" ([SPEC §Keys], `title`).
- OSC 21337 (iTerm2 session status) and OSC 9999 (Orca) are described as earlier, presentation-oriented attempts.

**Inference:** runny should not emit OSC 133. That is the shell's job, and the shell around runny already marks the command. runny should not touch the window title either. Emitting OSC 9;4 as well would be allowed but adds little; see §6.

### Unsupported terminals

- [SPEC §Feature detection]: "Terminals MUST ignore unknown OSCs, so a program MAY send reports without querying first." [POST] says the same thing.
- tmux is verified to swallow them silently ([TMUX], above).
- **UNCONFIRMED:** I did not audit other non-supporting terminals (Terminal.app, Alacritty, WezTerm, VS Code, conhost) to see whether any print garbage. In general, ECMA-48 parsers consume OSC strings up to ST/BEL. A very old or broken terminal, or output piped into a log file or CI viewer, would show the raw bytes. This is why runny should gate on TTY output (§5).

### Detection

- The query is `OSC 7501 ; ? ST`. A supporting terminal MUST reply with `OSC 7501 ; ?…` and may list `states=` and `kinds=`. To avoid a timeout, send DA1 (`CSI c`) right after the query: if the DA1 reply arrives first, the protocol is unsupported. Detection is optional. [SPEC §Feature detection]
- Ghostty's reply body is `?:states=idle,working,done,blocked,error:kinds=permission,question,auth`, terminated with whichever terminator the query used. [GH-PARSER `query_reply` L104; GH-STREAM L987-997]
- No environment variable is defined by the spec. **Inference:** `TERM_PROGRAM` sniffing would be a heuristic outside the spec. It is also unreliable, because Ghostty sets it but ignores the reports. Don't use it.

## 5. Practical concerns for a task runner (inferences/recommendations unless cited)

1. **Only emit to a TTY.** runny already uses `golang.org/x/term` (`term.IsTerminal`, `runny/model.go`). Emit on **stderr** when stderr is a terminal. This keeps `runny foo | jq` stdout clean, and stderr shares the pty with stdout in the normal case. Add an opt-out (e.g. `RUNNY_NO_STATUS=1`) and skip when `TERM=dumb`. Both are suggestions; neither is in the spec.
2. **Skip feature detection.** runny hands `os.Stdin` straight to child shells (`runny/shell.go`). Reading a query reply would need raw mode on stdin and could steal keystrokes or leave reply bytes for the child to read. The spec explicitly allows sending without querying.
3. **Child processes that also emit 7501.** Records are per terminal, not per process [SPEC §Records and ids]. If runny and a child (e.g. a future `brew` or `terraform`) both use the root record, the last writer wins. That is acceptable because runny writes only between child runs (`exec.Cmd.Run` is synchronous), so its final `done`/`error` will be the last report. Rules to follow:
   - **Never send `state=clear` without an id.** That wipes every record on the terminal, including children's. [SPEC §States]
   - Nested `runny` (a task whose `run:` calls `runny other`) also writes the root record. The inner `done` is quickly overwritten by the outer `working`/`done`, which is fine.
   - Alternative: give runny its own record via `id=runny` (or `id=runny/<task>`). This avoids clobbering a child's root record, but it means runny's status never becomes the window-level root status. I recommend the root record for simplicity.
4. **Atomic writes.** Build each report in a buffer and write it with a single `Write` so it can't interleave with other output. Writes only happen while no child is running, so interleaving with child output is not a concern.
5. **tmux / screen.**
   - tmux drops unknown OSCs ([TMUX] `input_exit_osc`). Passthrough is `ESC P tmux; <payload> ESC \` and only works when the `allow-passthrough` option is `on` (pane visible) or `all`. The default is `off`. ([TMUX-MAN L6490-6501](https://github.com/tmux/tmux/blob/a73616d781f2af13085691c741cfb0780d365328/tmux.1#L6490-L6501); `options-table.c` `default_num = 0`)
   - Inside the payload, every ESC must be doubled. This follows from tmux's DCS escape state table: after ESC, any byte other than `\` is appended to the buffer, so only the second ESC of a pair survives. ([TMUX L698-706](https://github.com/tmux/tmux/blob/a73616d781f2af13085691c741cfb0780d365328/input.c#L698-L706)) The wrapped form is `ESC P tmux; ESC ESC ] 7501 ; … ESC ESC \ ESC \`.
   - **Recommendation:** don't wrap by default. The outer terminal would attribute the status to the whole tmux window/tab, not the pane, and it silently fails without user configuration. If wanted, gate it on `$TMUX` plus an explicit opt-in. **UNCONFIRMED:** GNU screen passthrough behaviour (not researched).
6. **Cleanup on exit, signals, and panic.** Lifetime rules partly cover crashes: `working` is dropped when the next OSC 133 A prompt arrives [SPEC §States]. This only helps with shells that have shell integration, so runny must still emit a final state on every path:
   - Success: `done`. Failure (non-zero child or runny error during execution): `error`. Ctrl-C: `idle`, per the spec's "interrupts or cancels" rule.
   - Currently runny installs no signal handler, so SIGINT kills it outright. To report `idle`, add `signal.Notify(ch, os.Interrupt)`. The child, being in the same foreground process group, still gets SIGINT from the tty and exits. `cmd.Run` then returns, runny sees the interrupted flag, reports `idle`, and exits 130.
   - Side effect to consider: once runny catches SIGINT it no longer dies before its children, so `Then` steps must not run after an interrupt. They already won't, because `Execute` returns on the first error.
   - SIGTERM sent to runny alone would not reach children unless forwarded. I suggest leaving SIGTERM default for now.
   - `Run()` calls `os.Exit(1)`, which skips defers, so emit the final status **before** `os.Exit`. For panics, a `defer` with `recover()` in `run()` can emit `error` and re-panic.
7. **Windows.** **UNCONFIRMED** on all points:
   - Windows Terminal does not implement 7501 yet (see §4). I did not verify whether it, or conhost, ignores the sequence cleanly.
   - Raw escapes need VT processing enabled on the console. `fatih/color` uses `go-colorable` on Windows, but runny would write the status directly to `os.Stderr`.
   - runny already rejects `pwsh`/`powershell` as shells (`runny/shell.go`) and defaults to `/bin/bash`, so Windows use is probably via Git Bash/MSYS.
   - Suggestion: skip emission when `runtime.GOOS == "windows"` until someone verifies it.
8. **Message content.** `msg` is shown in terminal UI and maybe in OS notifications. Use the task name, not the full `run:` string, which may contain secrets passed through env/args. Strip control characters and cap at 2048 bytes before base64-encoding, because a report that breaks the rule is discarded whole. Task names come from YAML keys, so they could contain anything.
9. **Progress.** Leave it indeterminate. The step count is not known ahead of time because `If` conditions are evaluated lazily inside `Execute`.

## 6. Where status fits in runny (recommendation)

Relevant code:
- `runny/cmd.go` `run()`: parses flags, calls `readConfig`, then `runny.Execute(name, args...)`.
- `Run()`: prints the error and calls `os.Exit(1)`.
- `runny/model.go` `(*Config).Execute`: recursive. It evaluates `If` (and returns nil when it is false), runs `Needs` recursively, then `Run` through `shell.Run`, then `Then` recursively.

Proposed points:

| Point | Report |
|---|---|
| Top-level, just before `Execute` in `run()` | `working`, msg "Running <name>" |
| In `Execute`, after the `If` check passes and before `shell.Run(run, …)` | `working`, msg "<name>" (or "<top>: <name>" when it is a dependency/then step) |
| `Execute` returns nil at top level | `done`, msg "<name> finished" |
| `Execute` returns an error | `error`, msg "<name> failed: <err>" |
| SIGINT received during execution | `idle` (no msg) |
| Panic | `error`, msg "runny crashed" |
| Listing commands, `--help`, `--schema`, `--init`, config errors | **nothing**, because no work is happening |

Edge cases:
- An unknown command name is reported as an error by `Execute`. It's probably cleaner to check that the name exists before emitting `working`.
- A top-level `If` evaluating false returns nil. Report `done` with msg "<name> skipped", or emit nothing. This is a judgement call.
- `blocked`/`kind` don't apply. runny can't know whether a child is waiting on input. A child that knows should report that itself.

### Minimal sketch (no new dependency)

```go
// runny/status.go
package runny

import (
	"encoding/base64"
	"io"
	"os"
	"runtime"
	"strings"
	"unicode"
	"unicode/utf8"

	"golang.org/x/term"
)

// status emits OSC 7501 program-status reports
// (https://www.superlogical.com/rex/docs/build/program-status, rev 0.4).
// A nil *status or nil writer is a no-op.
type status struct{ w io.Writer }

func newStatus() *status {
	if os.Getenv("RUNNY_NO_STATUS") != "" || os.Getenv("TERM") == "dumb" || runtime.GOOS == "windows" {
		return nil
	}
	if !term.IsTerminal(int(os.Stderr.Fd())) {
		return nil
	}
	return &status{w: os.Stderr}
}

const maxMsgBytes = 2048 // spec limit on decoded msg

func (s *status) report(state, msg string) {
	if s == nil || s.w == nil {
		return
	}
	var b strings.Builder
	b.WriteString("\x1b]7501;state=")
	b.WriteString(state)
	b.WriteString(":app=runny") // repeat every time: each report replaces the record
	if msg = cleanMsg(msg); msg != "" {
		b.WriteString(":msg=")
		b.WriteString(base64.StdEncoding.EncodeToString([]byte(msg)))
	}
	b.WriteString("\x1b\\")
	io.WriteString(s.w, b.String()) // single write; errors deliberately ignored
}

// cleanMsg replaces control characters (which make terminals discard the
// whole report) with spaces and truncates on a rune boundary.
func cleanMsg(s string) string {
	s = strings.Map(func(r rune) rune {
		if unicode.IsControl(r) { // covers C0, DEL and C1
			return ' '
		}
		return r
	}, strings.ToValidUTF8(s, "?"))
	for len(s) > maxMsgBytes {
		_, size := utf8.DecodeLastRuneInString(s)
		s = s[:len(s)-size]
	}
	return strings.TrimSpace(s)
}
```

Wiring in `runny/cmd.go` `run()` (sketch):

```go
	args := flags.Args()
	if len(args) > 0 {
		name := CommandName(args[0])
		if _, ok := runny.Commands[name]; !ok {
			return fmt.Errorf("unknown command: %s", name)
		}
		st := newStatus()
		runny.status = st // new unexported field on Config

		var interrupted atomic.Bool
		sigs := make(chan os.Signal, 1)
		signal.Notify(sigs, os.Interrupt)
		defer signal.Stop(sigs)
		go func() { for range sigs { interrupted.Store(true) } }()

		defer func() {
			if r := recover(); r != nil {
				st.report("error", "runny crashed")
				panic(r)
			}
		}()

		st.report("working", "Running "+string(name))
		err := runny.Execute(name, args[1:]...)
		switch {
		case interrupted.Load():
			st.report("idle", "")
			os.Exit(130)
		case err != nil:
			st.report("error", fmt.Sprintf("%s failed: %v", name, err))
			return err
		default:
			st.report("done", string(name)+" finished")
		}
	}
```

And in `(*Config).Execute`, immediately before `shell.Run(run, args, true, …)`:

```go
		c.status.report("working", string(name))
```

Notes on the sketch:
- With `signal.Notify(os.Interrupt)` in place, runny outlives its child on Ctrl-C instead of dying with it. Check that this is acceptable. In particular, a child that traps SIGINT and keeps running would keep runny alive too, which is arguably correct.
- Tests can construct `&status{w: &bytes.Buffer{}}` and assert on the exact bytes. Also test `cleanMsg` with newlines, C1 controls and over-long input.

## Open questions / unconfirmed

1. What exactly does "the process attached to the terminal exits" mean? Most likely the pty's session leader (the shell), not runny, so runny's exit alone doesn't drop its `working` record. [SPEC] does not define it precisely. This is another reason to always emit a final state.
2. How do non-supporting terminals other than tmux behave (Terminal.app, Alacritty, WezTerm, VS Code, conhost/Windows Terminal)? Not audited.
3. GNU screen passthrough was not researched.
4. When will the Ghostty app actually consume reports? It currently ignores them. When will kitty 0.50.0 ship? Neither is known.
5. The spec is still pre-1.0 (rev 0.4, four revisions in two weeks). Expect changes. The fixed state/kind lists and the "unknown keys ignored" rule are designed to keep existing emitters valid.
6. Whether runny should also emit OSC 9;4 for terminals that support only that (allowed by [SPEC]) is a product decision. I did not verify which terminals support 9;4.
